# RCA — RISEDUAL "alpha" prod: alpha-v2 health `broker_reachable:false`, `account:null`

**Scope:** READ-ONLY production diagnosis. Nothing was changed.
**Deployment:** `algo-trader-ai-1` (risedual.ai / www.risedual.ai) · live URL `https://algo-trader-ai-1.emergent.host`
**Active run:** `621e3bd0-30ca-4467-a5f4-42fb615371bd` (redeploy, status success, 2026-09-23 22:41Z) — this is what is serving.
**Prod DB actually used:** `risedual-trading-tradealgo_db` (resolved from the deployment `DB_NAME` secret).

## Verdict
**Root cause = (b): there is NO Public record in the production Mongo the app actually reads.**
The alpha-v2 resolver runs the latest 3-source code, finds nothing for `broker_id:"public"`, and returns `None` — so `PublicBroker.from_db` reports the broker unreachable with a null account. It is NOT a stale image, NOT a shape mismatch of an existing row, NOT a decryption/key failure, and NOT a Public JWT/get_account failure (the resolver never gets far enough to call Public).

## Evidence per question

### 1) Is the latest code (3-source `_aresolve_connect_creds`) actually deployed? YES.
- Pipeline state: active run `621e3bd0` succeeded; it is the promoted/live run.
- Deployed source (pulled archive for `621e3bd0`, `backend/services/public_equity_live_executor.py`, `async def _aresolve_connect_creds` at line 630) contains the full priority chain:
  1. env `PUBLIC_API_KEY` + `PUBLIC_ACCOUNT_ID`
  2. plaintext `broker_connections {broker_id:"public", status:"connected"}` reading `api_key`/`api_secret`
  3. panel `broker_connections {broker_id:"public", is_active:true}` decrypting `api_key_enc`/`api_secret_enc` via `_decrypt_or_none`, preferring the explicit `account_id` field.
- So the "older image where the resolver only reads the status:connected row" hypothesis is **ruled out** — the encrypted-panel branch is present in the live image.

### 2) Public record in prod `broker_connections`? NO.
Query against the live prod DB `risedual-trading-tradealgo_db`:
- `find {broker_id:"public"}` → **0 documents**.
- `distinct broker_id` → `["alpaca","kraken"]` only.
- Full collection = **2 docs**, both encrypted-panel shape (`is_active:true`, `api_key_enc`, `api_secret_enc`, `account_id`, `connected_at`, `paper:true`), for `kraken` (account_id `kraken`) and `alpaca` (account_id `PA34S5WPONEH`). No `status:"connected"` plaintext row for anything.
- Also checked `api_key_vault` for `{broker_id:"public"}` → 0.
- Secret values were NOT read (read-only, values never exposed) — but the presence check is conclusive: no public row of any shape exists.

### 3) Are `CREDENTIAL_ENC_KEY` / `JWT_SECRET` present, and would decrypt succeed? Keys PRESENT; decrypt not the issue.
- `list_secrets` (live run): `CREDENTIAL_ENC_KEY` is_empty=false, `JWT_SECRET` is_empty=false — both set.
- The existing kraken/alpaca rows use `api_key_enc` and carry recent `last_used` timestamps, i.e. the prod pod's Fernet key decrypts real encrypted rows successfully. There is therefore no evidence of a key-mismatch decrypt failure.
- Neither `PUBLIC_API_KEY` nor `PUBLIC_ACCOUNT_ID` exists in the prod secret set (resolver source #1 is unavailable).
- Because there is no public row, decryption of a public credential never even runs — cause (d) is moot/ruled out.

### 4) Error/warning logs from the resolver/broker around the health calls? NONE.
- App logs (active run, 24h) around the `GET /api/admin/alpha-v2/health` call show only unrelated `services.provider_pool` AlphaVantage warnings ("AV daily failed / rate limited") plus one `GET /api/admin/alpha-v2/health HTTP/1.1 200 OK`.
- No `[public-live] broker_connections lookup failed`, no `credential decrypt failed`/`_decrypt_or_none`, no `PublicTradingService` init/auth/get_account errors.
- This is exactly the fingerprint of the resolver taking the silent `return None` path (env miss → plaintext miss → panel miss), not an exception path. Confirms (e) is ruled out too.

## Why prod has no public row (mechanism)
There is a real environment/DB-name discrepancy:
- Preview `.env` (in the pulled source): `DB_NAME=risedual_db`, `RISEDUAL_DB_NAME=risedual_db`.
- Production actually runs on `DB_NAME=risedual-trading-tradealgo_db` (deployment secret; preview `.env` values do NOT overwrite existing deployment secrets on redeploy).

The operator reports a working plaintext Public row exists in preview (`risedual_db`) and preview health is green. That row is in the **preview** database, which the production pod never reads. The most likely explanation is that the `POST /api/broker/connect` that "connected Public in production" was actually executed against the preview environment (or otherwise never persisted to `risedual-trading-tradealgo_db`). Both `/api/broker/connect` and the health endpoint use the same app DB handle, so within prod there is no split-brain — prod simply has no public connection row.

## Remediation options (operator action — no code change required; latest code is already live)
Either one fixes it:
1. **Re-connect Public.com against PRODUCTION.** Log into the live prod app (risedual.ai / algo-trader-ai-1.emergent.host) and run the broker-connect flow there, so an encrypted panel row `{broker_id:"public", is_active:true, api_key_enc, api_secret_enc, account_id}` lands in `risedual-trading-tradealgo_db.broker_connections`. Then re-check `/api/admin/alpha-v2/health`. Verify a public row now appears (distinct broker_id includes "public").
2. **Set env creds as prod secrets (fastest, resolver source #1):** add `PUBLIC_API_KEY` (the Public API secret) and `PUBLIC_ACCOUNT_ID` (account number) in Deployment Panel → Secrets, then redeploy. The resolver returns these before any DB lookup, making `broker_reachable` true without touching the DB.

Note: option 2 requires setting the values in the Deployment Panel → Secrets UI and redeploying (new deployment secrets are added from preview `.env` on redeploy, but existing ones are not overwritten). Whichever path is chosen, confirm afterward via `/api/admin/alpha-v2/health`.
